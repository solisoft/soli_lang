# Bytecode VM

Production `soli serve` compiles each handler to bytecode and runs it on a stack machine. `--dev` does not. Scripts (`soli script.sl`, `soli -e`, `soli build tool.sl` executables) run on it too, unless they need the tree-walker — see the engine table in [Internals](/docs/internals).

```
src/vm/
  opcode.rs           # Op enum
  chunk.rs            # bytecode + constants (CompiledModule, FunctionProto)
  compiler.rs         # Compiler + compile()
  compiler_exprs.rs   # expressions
  compiler_stmts.rs   # statements
  compiler_classes.rs
  compiler_patterns.rs
  compiler_hoist.rs   # optional-let: which bare locals are hoisted, which declared in place
  compiler_script_locals.rs  # which top-level variables of a script get frame slots
  compiler_fold.rs    # constant folding of literal arithmetic
  compiler_literal_arrays.rs  # array literals made of literals, and membership in them
  literal_list.rs     # their constant (Constant::LiteralList) and its run-time half
  vm.rs               # Vm, CallFrame, run() dispatch loop
  vm_calls.rs / vm_classes.rs / vm_exceptions.rs
  vm_*_methods.rs     # String/Array/Hash/Int/primitive methods
  upvalue.rs          # VmClosure, Upvalue cells
  vm_upvalues.rs      # closures: making, capturing, closing, reusing
  method_table.rs
  disassembler.rs
```

## Compile

```rust
impl Compiler {
    pub fn compile(program: &Program) -> CompileResult<CompiledModule>
    pub fn compile_with_globals<I>(program, global_names) -> CompileResult<CompiledModule>
    pub fn compile_entry_script(program, kernels, is_builtin) -> CompileResult<CompiledModule>
    pub fn compile_method_standalone(...) -> ...
}
```

`compile_with_globals` is what serve uses: the worker already knows global names (`User`, `render`, …), so a bare assignment inside a handler becomes a local, matching the tree-walker. `compile_entry_script` is what `soli script.sl`, `soli -e` and script executables use (`execute_program` in `lib.rs`); see *Top-level variables of a script* below.

Soli's optional `let` — `total = 0` with no `let` creates the binding — is compiled by hoisting: `compiler_hoist.rs` collects every name a function body assigns bare, and `hoist_locals` declares each one as a local of the whole function unless it is a parameter, an enclosing local (it stays an upvalue) or a known global (the assignment updates it). Where it declares one depends on the first mention of the name. If that is a top-level statement of the body, `name = value`, and no earlier statement and not `value` mentions the name anywhere (closures and nested `def`s included), the statement declares it in place, as `let name = value` would: the value stays on the stack as the slot, with no store and no `Pop`, so straight-line bare locals compile to the same bytecode as `let` (`in_place_declarations`). The others are hoisted: their slots are filled with nil at function entry, one `PushNulls(n)` for all of them, and every assignment stores into the slot. That covers a name first assigned in a branch, a loop or a block, which stays function-wide, and a name read or captured before its first assignment, which reads nil. Because a name the planner misses would compile against the global, a global resolution of a pending name refuses the function (it runs on the interpreter). At file scope, `SetGlobal` defines a name that does not exist yet. Up to 2.6.1 this was off unless `SOLI_VM_OPTIONAL_LET=1`: a bare assignment to a new name compiled to `SetGlobal` and raised *Undefined variable* at run time, so nearly every real action was re-run on the interpreter — and one that had already written to the database could not be re-run, and answered 500. It is now on; `SOLI_VM_OPTIONAL_LET=0` restores the old behavior as an escape hatch.

**Top-level variables of a script.** At file scope `n = 0`, `let n = 0` and `const N = 0` compile to globals (`DefineGlobal`/`SetGlobal`, read back with `GetGlobal`): every access hashes the name and no local super-instruction applies, so a loop over them runs 4–6× slower than the same loop in a `def`. `compile_entry_script` keeps a top-level variable in a frame slot of the main chunk instead, declared in place like a bare local in a function (it reuses `in_place_decls`), when nothing but the script's top-level code can reach it. `compiler_script_locals::plan` decides, by name, all or nothing: the name's first mention must be its top-level `name = value` / `let` / `const` statement (as in a function body, a name read earlier stays a global and keeps its *Undefined variable*); no `def`, lambda, block, class, enum or module anywhere in the program may mention it (they would capture the slot, or read the global from their own frame); it must not be a builtin the script assigns (`is_builtin`, the interpreter's bindings: a prelude function reads the replaced builtin by name, as on the tree-walker); and a program that calls `defined` or `const_get` keeps every name global, since those ask for a global by a name known only at run time. At most 256 names are planned (`MAX_SLOTS`: pending plans are searched linearly, and slots are `u16`). Names a block writes, such as `total` in `xs.each do |x| total += x end`, therefore stay globals. A planner miss cannot change what runs: a source-written function capturing a slot raises the shared `promotion_guard`, a read or write before the planned statement refuses it as in a function, and either way the program is compiled again with every top-level name a global. A lambda the compiler makes up for a mid-expression comprehension or `match` (`wrap_in_lambda`, `expr_wrapper`) may capture a slot: it is called on the spot. `Compiler::compile`, serve handlers, views and the cached `run_vm` path keep top-level names global, because their callers read them back from `Vm::globals`.

**Constant folding.** `compiler_fold::fold` turns an operator on number or string literals into one constant: `60 * 60 * 24` is `Constant(86400)`, `-1` no longer needs a `Negate`. It computes with the VM's own arithmetic — checked `Int` `+ - * / %` (truncating `/` and `%`), `Float` and mixed `+ - *`, `Float / Float`, `String + String` — and folds nothing that would raise (an overflow, a zero divisor) or that it does not mirror exactly (mixed `/`, `Float %`, comparisons), so those still run and raise at run time. It is off under line coverage, which marks each operand's line as it compiles.

**Array literals made of literals.** An array literal whose elements are all string, number, boolean, nil or symbol literals (parenthesized or folded ones too: `-1`, `60 * 60`) keeps them in one `Constant::LiteralList` (`compiler_literal_arrays.rs`). `["draft", "sent"]` is then one `LiteralArray`, which builds a new array from the constant on every evaluation, instead of a `Constant` per element (a string constant leaves the fast tier) and an `Array`. The membership test the style guide and `idiom/prefer-includes` recommend — `["up", "late"].includes?(status)`, also `include?`, `contains`, `contains?`, with one positional argument — compiles to the argument and one `LiteralListIncludes`: no array is built and no method is dispatched. It compares as `Array#includes?` does on both engines, `element == needle` with `Value`'s `==`; the fast tier answers a string, number, symbol, boolean or nil needle inline (`LiteralList::contains_scalar`) and hands any other needle (a class equals the string of its name, a `grouped {}` placeholder compares as its value) to the general arm, which compares the long way. The op keeps the user-method gate of the call it replaces: `includes?` and `contains?` have no method id and compiled to `CallMethod`, so a user-defined Array method of that name still takes the call (the op then builds the array and calls it); `include?` and `contains` compiled to `CallMethodById`, which has no gate, and so has none here. Under line coverage the literal's lines are still marked, in the order compiling each element marked them.

**Ranges a loop walks.** `for x in a..b` and the list and hash comprehensions over `a..b` compile the two bounds and `GetIterRange`, and step with `ForIterRange` (`compile_iterable`): no array is built, so nothing is allocated for the range and `SOLI_MAX_RANGE_LEN` does not limit it. A comprehension still builds its result, so over a range each element ends with `PopRangeComprehension` instead of `Pop`, which refuses once the result holds more than `SOLI_MAX_RANGE_LEN` elements (`limits::check_comprehension_len`, called by the tree-walker's comprehensions too, at the range's line and column): without it `[i for i in (0..params["n"].to_i)]` grew until the allocator failed and aborted the process. Parentheses around the range are peeled first (`Expr::without_parens`), so `for i in (0..n)` is the same loop; it used to compile `Op::Range` and walk the array that built, 24 bytes an element. `GetIterRange` records the range's own line and column, where a bound that is not an integer is reported, as on the tree-walker, which counts through the same ranges (`execute_for_loop`, `comprehension_items`, `evaluate_range_bounds`). A range used any other way — as a value, a method's receiver as in `(1..51).map { … }`, a spread — is still built by `Op::Range`.

Every controller action runs on the VM, with or without a `(req)` parameter (`call_class_method` in `serve/mod.rs`); a zero-parameter action reads the request through the `req` global the worker publishes. An action that raises on the VM is re-run on the interpreter only while it has not written (`clear_durable_commit`); after a write the error is the response. So a VM gap is a 500 as soon as it follows a write, and the rule is to close gaps rather than rely on the fallback. The action leaves the VM for the rest of the worker's life (`Vm::failed_handlers`) in three cases, decided by `demote_on_vm_failure` and then `settle_engine_divergence`: the VM refused it (`EngineFallback`), the re-run succeeded where the VM failed (a divergence), or it failed after a write, where nothing can tell whose error it was. An error the re-run raises too is the app's own, and the action stays on the VM. Hooks and middleware follow the same rule. Where the interpreter already holds the single definition of a behavior, the VM delegates to it instead of copying it:

- **Model instances** — a member the VM would not answer the same way (a relation, a preload, a translated field, an unset column, uploader and HABTM helpers) goes through `Interpreter::instance_member_access` (`Vm::model_instance_member`); a bound helper it returns is called through `call_method` with the VM's globals.
- **Query builders** — members resolve through `query_builder_member_access` and calls through `call_query_builder_method`. Methods taking a block (`each`, `map`, `filter`, …) materialize the rows and run on the VM's own array methods, so a compiled closure is always called by the VM that owns its upvalues. `find_each`/`in_batches` still demote.
- **Methods that exist only as AST** — inherited from a class the VM never compiled — are compiled as methods on first use and cached in their defining class's `vm_methods` (`compile_tree_walking_method`), so `this` stays the receiver.
- **`super` in those classes** — `super(...)` and `super.m()` resolve against the superclass of the class on the running frame (`frame_superclass`), so every frame that runs a tree-walker constructor or method records the class that *declares* it, as the tree-walker binds `__defining_superclass__` where the class is declared: a constructor (`find_constructor_with_class`, in `call_class`, `call_init_of` and value objects), a method reached through `super.m()`, an invariant or a model callback (`find_method_with_class`), and the served action itself (`call_method_bound`, through `Class::declaring_class_of`). An inherited one runs as its declaring class's, so the next `super` goes one level further up instead of back into it. A frame with no class has nothing to resolve against and raises "super used outside of a subclass method" — which is still what a block's frame does (`super` in `xs.map { … }` inside a method).
- **Declared fields** — every construction starts the instance's declared fields before any constructor runs, the farthest class first, as `Interpreter::initialize_instance_fields` does: each class sets its fields (a literal default, else `nil`), then runs its defaults that are not literals on the new instance, in declaration order, before the next class down sets its own. Each class keeps a `FieldInit` (`Class::field_init`): every declared instance field with the value it starts with (its literal default — numbers, strings, symbols, Decimals, arrays and hashes of them — copied per instance, else `nil`), plus one method (`__field_defaults__`) that evaluates the defaults that are not literals on the instance and stores each with a raw write (`Op::InitProperty`; it returns `nil`, no hash). The compiler records the first through `Op::Field`, which receives the literal or `nil` (an initializer is never evaluated when the class is defined), and compiles the second with the class (`compile_field_defaults`). `op_add_method` keeps that method out of `vm_methods`. A class the tree-walker defined gets its `FieldInit` from its AST on the first instance the VM builds (`Compiler::compile_field_defaults_standalone`, in `Class::defaults_env`, the environment its methods see). Each class also keeps a `ConstructPlan` (`Class::construct_plan`), built on its first instance from its chain's `FieldInit`s: every field's start in one list, and the chain's defaults methods. `call_class` (and a labelled construction, and `Klass.new()` without attributes) starts the fields from it in one loop, then pushes one frame per defaults method above the constructor's frame — or above the instance when there is none — marked `FrameReturn::Discard`, so they run first, in the same activation, and their value goes nowhere (at the edge of a nested run, the run's value is the instance beneath). A chain where a class below one with such defaults declares fields of its own (`ConstructPlan::class_by_class`), the attribute form `Klass.new({..})` / `Klass.new(k: v)`, value objects and native constructors set the fields before going on, so they run the methods to completion (`init_fields`). The tree-walker evaluates the same defaults in `Class::defaults_env` with `this` the new instance; it evaluated them in the caller's environment, in hash-map order. A model's `Model.new(attrs)` (`member::new_with_attributes`) sets only literal defaults (`start_literal_defaults`), leaving a field it is not given unset, so `save` does not write a `nil` over a column default. Up to 2.29.3 the defaults lived in `init`: a field without one was never set ("Cannot access property"), `super()` re-applied the parent's after the child's, a served class got none, and a value object got `nil` in place of its default.
- **Constructors of those classes** — a tree-walker constructor is compiled once, in constructor mode (`Compiler::compile_constructor_standalone`: the body as statements, then `this`), and kept on the class that declares it (`Class::vm_constructor`, next to the function it was compiled from, compared by pointer). `Vm::resolve_constructor` hands `call_class` and `call_init_of` the nearest class's constructor, compiled either way — a VM class's (`Class::vm_init`) or this one — and both enter it as an ordinary frame with the instance as `this`, which the frame returns. Value objects run the same closure to completion, since freezing and invariants follow it. In a constructor, `return` (and a `break`/`next` outside a loop) evaluates its expression, drops it and returns `this`, as the tree-walker discards a constructor's value. A VM class's constructor is registered by `Op::Method` under a name no identifier can spell (`VM_CONSTRUCTOR`) and kept in `Class::vm_init`, never in `vm_methods`: a user method named `init` is a method like any other. It was kept as the method `init`, so `new Service()` ran a user's `def init` and a served class's `init`, once compiled, became its constructor. Up to 2.29.3 every `new` of a served class looked the constructor up as a method, wrapped it in a new closure and ran it in a nested `run()` only to throw its value away, and an early `return` in a VM class's constructor made the `new` itself `nil`. `Klass.new(args)` calls `call_class` with the arguments where they already are (`class_new`), and `Class::intercepts_new` keeps its answer until `note_static_methods_changed` bumps `STATIC_METHODS_EPOCH` (`include`, `extend`, a static joining a class). A new instance's field map is sized for every field its chain declares (`Class::declared_field_count`), a model row's for its columns (`Instance::with_capacity`).
- **Hash members** — a bare `hash.name` is `Interpreter::hash_member_value` on both engines, in this order: a Hash user method, the key (even one named like a builtin: `{"size": 2048}.size` is 2048), the universal members, then a builtin method name, as the method. `GetProperty`/`GetLocalProperty` answer a key hit first, in `run_fast` and in the general arms, and only while no Hash user method exists. Any shortcut added there must give the same answer: a builtin may answer only after the key misses. A call `hash.name(…)` means the method (`CallMethod`, and `Interpreter::hash_callee_value` on the tree-walker). These used to disagree: the tree-walker put the builtins before the key, so `soli test` read `row.size` as the entry count where production read the field.
- **Operators** — the dispatch loop computes `+ - * / %` and the orderings inline only for Ints and Floats (and `+` of two strings). Every other pair goes to the slow arm (`Vm::op_add` … `op_compare_less_equal`), which calls the interpreter's `Interpreter::eval_add` … `eval_modulo` and `compare_ordered` (`interpreter/executor/operators.rs`). So Decimal arithmetic, `Array - Array`, string repetition, the overflow and division-by-zero errors and DateTime ordering each have one definition. A new operand type goes there, plus a differential case. The VM's earlier copies had drifted: they had no Decimal arm, so every action doing Decimal arithmetic was demoted and every such view rendered twice.

On constructs the compiler cannot represent, it returns an engine fallback. The server then runs that handler on the interpreter (and `SOLI_FAIL_ON_VM_DEMOTION=1` turns that into a process exit in CI).

## Module / function prototype

`CompiledModule` holds function prototypes and the constant pool. `FunctionProto` is one callable: arity, bytecode, upvalue descriptors, name.

A literal is converted once, when it is compiled, never at each load. A Decimal literal's `Constant::Decimal` holds its `DecimalValue`, built by `DecimalValue::from_literal`, which the tree-walker uses too; its precision is the number of digits written after the point. So loading it is a copy and stays in the fast tier. Text that does not parse is a compile error: an integer part past Decimal's range, or a `%n[...]` word that is not a number. The code then runs on the tree-walker, which raises *Invalid decimal literal* where the literal is evaluated. The VM used to re-parse the text on every load and read such a literal as 0.

`compiled_cache.rs` (crate root) memoizes compile by source so workers don’t recompile identical files.

## `Op`

`src/vm/opcode.rs` — each instruction is a variant (load constant, add, call, jump, …). Adding an opcode means:

1. Variant on `Op`
2. Emit site in the compiler
3. Arm in `Vm::run_dispatch` (the big `match`)
4. Disassembler string
5. If it is hot and simple, an arm in `Vm::run_fast` too (see below)
6. Its net stack effect in `stack_effect` (`compiler.rs`), and a case in `stack_effect_matches_what_each_handler_does`, which runs the handler on a VM and compares stack heights. The compiler reads that table to tell whether the stack holds only locals before it gives a comprehension or a binding `match` a slot. If a value is more negative than the handler's real effect, the gate sees a clean stack that is not clean.

`vm.rs::run_dispatch` is a large match by design (dispatch). Don’t split it for style.

A peephole fusion (`peephole_optimize_chunk`) must leave the stack exactly as the sequence it replaces does: same net effect, same value on top. `SetLocal` peeks instead of popping, so a sequence ending in it still holds its value. When the fused op pushes nothing, the statement's trailing `Pop` must be part of the pattern, as it is for `IncrLocal`, `AddLocalConstInPlace` and `AddNestedIndex`. A shape the fusion cannot keep exact is left unfused. `x = x` is one: fusing it into `SwapSetLocal` lost a slot, swapped two locals and panicked on the next read.

Rules are tried in order at each head, and the first match wins, so a rule placed after one that takes the same prefix never fires. Through 2.29.3, five-op `a = a - b`, `* b` and `/ b` rules sat behind the three-op `SubLocalLocal`/`MulLocalLocal`/`DivLocalLocal` ones, a copy of `AddLocalsInPlace` sat behind it, and two `AddLocalInt` rules sat behind `AddLocalConst`. They are removed, so nothing emits `AddLocalInt` or `AddLocalLocal` now. What the five-op rules aimed for comes from the pass's last step, `fuse_set_local_pop`. It turns the `SetLocal, Pop` that ends an assignment statement (and a re-`let`, and each `match` arm) into one `SetLocalPop`, which moves the value into the slot instead of copying it there and dropping the copy. It runs after every other rule, so a pattern that ends in the pair (`IncrLocal`, `AddLocalsInPlace`, `AddNestedIndex`) still takes it. So does `k += c`, `k -= c` or `k *= c` with an Int or Float constant that is not `+= 1`/`-= 1`: the five ops become `AddLocalConstInPlace`, `SubLocalConstInPlace` or `MulLocalConstInPlace`, which write the slot and push nothing, where the three-op `AddLocalConst` read would have left `AddLocalConst, SetLocalPop` (two dispatches, a push and a pop). Their fast arm takes two Ints (checked) or two Floats; an overflow, a mix or any other type goes to the general arm, which applies `AddLocalConst`'s rules and stores the result (`self_arithmetic_with_a_constant_is_one_in_place_op` in `compiler.rs`). A branch may land on the `SetLocal`: `x = a || b`, a ternary, a `match` and `rescue` all merge there. It must not land on the `Pop`: `ok && (x = 1)` as a statement short-circuits to that `Pop` with `ok` on the stack, so the pair stays. The peephole tests in `compiler.rs` (`assignment_statements_store_with_set_local_pop`, `a_store_whose_pop_a_branch_lands_on_keeps_it`) pin both.

The same rule holds for every pattern, not only the store: a branch may land on a pattern's first instruction but never inside it. Each rule writes its fused op at the head's own index and blanks only the tail, `compact_nops` maps a branch to the head onto the fused op, and `any_jump_target(&is_jump_target, i + 1, n)` refuses the fusion when a branch lands in the tail. Through 2.29.3 the scan also skipped any head that a branch landed on, before trying a rule. That left every `while` condition (the `Loop` target), the statement after each `if`/`elsif`/`else`/loop/guard/`catch`, every `elsif` and `else` head, match arms 2..n and the first statement of a function with a defaulted parameter unfused: `while i < n` ran as `GetLocal, GetLocal, TestLessJump` instead of `LessLocalLocal, JumpIfFalse`, and `i += 1` right after an `if` as five ops instead of `IncrLocal`, about 25% slower than one line earlier. `a_pattern_a_branch_lands_on_still_fuses`, `a_counting_while_loop_is_four_ops` and `a_branch_into_the_tail_still_blocks_the_fusion` (`compiler.rs`) pin it, and the `fused_head_*` differential cases run each target kind on both engines.

**Branch offsets are 16 bits.** Every jump, loop and handler operand (`Jump*`, `Loop`, `ForIter*`, `TryBegin`, `CatchMatch`, `JumpIfParamSupplied`…) is a `u16`, written through `Chunk::jump_operand`: a distance past `chunk::MAX_JUMP_OFFSET` (65,533, which leaves room for the `+ 2` a fused `JumpIfLocalTruthy` adds) marks the chunk (`offset_overflow`), and `check_jump_offsets` refuses the function, a function nested in it or the script, before the peephole runs, so the code runs on the tree-walker. Up to 2.29.3 the distance was truncated: a body of more than 65,535 instructions jumped into its own middle and, with `peek_two!`'s unchecked reads, read past the stack. Never write a branch operand with `as u16`; `compact_nops` only shortens offsets, so it keeps them in range.

### Labelled calls

`f(k: v)` compiles to `CallNamed` / `NewNamed`: the callee, then every argument in source order, with a `Constant::ArgNames` labelling each slot. `call_value_named` binds them once the callee is known — by name into a compiled function's parameter slots (`bind_named_arguments`), or as one trailing options hash for a native.

A labelled call on a **member** keeps its receiver: `obj.m(k: v)`, `this.m(k: v)`, `@m(k: v)` and `obj&.m(k: v)` compile to the receiver, the arguments, then `CallMethodNamed(name, argc, names)`; the bare helper `m(k: v)` in a method to `SelfOrGlobalCallee` + `CallSelfOrGlobalNamed`. `Vm::call_method_named` resolves the method as `call_method_slow_path` does (an instance's compiled or tree-walker method, a class's static), binds with `bind_method_arguments` and opens the frame with the receiver in the callee slot. A block's slot is labelled `chunk::BLOCK_LABEL` (`&`): it goes to the `&block` parameter that `FunctionProto::block_param` records, or is dropped, as on the tree-walker. Anything else — a native instance method, `with`, `method_missing` — takes the positional path with the labels as one options hash; a field, `Klass.new` or a model scope is read and called as `CallNamed` calls it. Up to 2.29.3 every labelled member call was a property read plus `CallNamed`, which lost the receiver: a VM class failed ("Cannot access property 'm'"), a served class ran the method with the function itself as `this`, and a method of arity 0 ran once on the read.

### The fast tier (`run_fast`)

Before the big `match`, `run_dispatch` calls `run_fast`, which runs the simple ops with the current frame's `ip`, code, constants and stack base held in locals — `&mut self` otherwise forces a reload of all of them through `self.frames` on every op. It covers locals, upvalues (reads, writes, and `+=` on numbers), global reads, constants, jumps, integer/float arithmetic and comparisons, the fused local super-instructions, making a closure and closing a scope's captured locals, hash key reads (`row.title`), instance field reads and writes (`@x`, `post.title`, `@x = v`), instance method calls (`post.summary()`, `@helper(x)`, `this.total(a, b)`), and the common shape of `Call`/`CallGlobal`/`Return` (a compiled closure given every required argument and no more than it declares, `arity <= argc <= params`, each omitted parameter getting a nil slot that its default-value prologue fills; a return that stays in this `run`, which closes its frame's captured locals on the way out), switching its cached state to the new frame.

The rule that keeps the two tiers from disagreeing: **a fast arm either completes its op or hands it back untouched.** Type and overflow checks peek before anything is popped; anything else — a string `+`, an overflow, a native callee, an error to raise — `break`s out with the op, `ip` is written back, and the general arm runs it exactly as if the fast tier did not exist. So a new op needs only a general arm to be correct; a fast arm is an optimisation, and must never produce an error or a result the general arm would not. `tests/differential_engines_test.rs` (`fast_tier_hands_off_to_the_general_arm`) exercises the hand-offs.

The general arm is where an overflow lands, so it must check every Int it computes: `checked_add`/`checked_sub`/`checked_mul`, raising `operators::int_overflow` before the slot is written, as `Op::Add` does. A bare `a + b` wraps silently, because the release profile has no `overflow-checks`; debug builds panic instead. `IncrLocal`, `DecrLocal`, `AddLocalsInPlace` and `AddNestedIndex` wrapped like that through 2.29.3: `i += 1` on the largest Int gave the smallest. `int_overflow_in_fused_local_ops_raises` (differential) and `fused_int_ops_raise_on_overflow_instead_of_wrapping` (`vm.rs`) pin it.

Equality is the other thing a general arm must not write for itself. Every op that compares two values for `==` or `!=` decides with `values_equal`, fused or not: `Equal`, `NotEqual`, `TestNotEqualJump`, `EqualLocalLocal`, `NotEqualLocalLocal`, and `EqualLocalConst`/`NotEqualLocalConst` past their inline pairs. It compares Ints and Bools inline and gives everything else to `enum_aware_equal`, which the tree-walker's operators call too. `PartialEq` on `Value` is not `==`: it compares two instances by pointer, so two equal enum values built apart (any payload variant, or an `enum_field` read rebuilt from storage) differ under it. `TestNotEqualJump`, the fused `!=` that ends a condition, used it through 2.29.3, and `if a != b` took the branch that `a != b` as a value did not. `enum_not_equal_in_a_condition` (differential), `enum_values_compare_by_value_in_every_equality_op` and `not_equal_conditions_compare_enum_values_by_value` (`vm.rs`), and `a_view_compares_enum_values_by_value_in_a_condition` (`vm_template.rs`) pin it.

The fast tier answers `==`/`!=` itself only between two **primitives** — Int, Float, Bool, nil, String, Symbol — through `primitive_equal` (and `primitive_equal_constant` for the `*LocalConst` ops, which compare a local with a pool entry in place). It is `values_equal` restricted to those kinds: the same kind compares by value, two different kinds are never equal, and an Int against a Float is handed back, because they compare as numbers. Anything else is handed back too: a `grouped` read must be forced, an enum compares structurally, a class equals its name. `primitive_equal_agrees_with_values_equal` (`vm.rs`) checks every pair it answers. A string or symbol operand owns a reference count, so those arms pop and drop it instead of overwriting the slots as the scalar arms do.

The compiler emits the fused forms: `GetLocal, Constant, ==|!=` becomes `EqualLocalConst`/`NotEqualLocalConst` for any constant (`x == 0` included: `IsZeroLocal`/`NotZeroLocal` are no longer emitted), `GetLocal, GetLocal, ==|!=` becomes `EqualLocalLocal`/`NotEqualLocalLocal`, and `Equal, JumpIfFalse` becomes `TestEqualJump` for a condition whose left side is not a bare local (`if h["k"] == "z"`). A literal `match` arm compiles straight to `EqualLocalConst(subject, literal), JumpIfFalse`, so it does not wait on the peephole. String constants and `Symbol` are served in the fast tier as well (an `EcoString` clone never allocates). Through 2.29.3 none of the fused equality ops was emitted, and `role == "admin"` cost two round trips to the general arms. `equality_compiles_to_fused_ops` (`compiler.rs`), `string_literals_and_primitive_equality_stay_in_the_fast_tier` (`vm.rs`) and `equality_fused_and_fast_paths` (differential) pin it.

Division, `??` and reads by key or index stay in the fast tier as well, each on the cases its general arm answers without raising or converting. These are `DecrLocal` above `i64::MIN`; `/` and `%` on two Ints when `checked_div`/`checked_rem` answers, and `/` on two Floats with a non-zero divisor, in the stack form and in `DivLocalLocal`/`ModLocalLocal`/`DivLocalConst`/`ModLocalConst` (all through `fast_quotient`); `NullishJump` (`??`, `??=`), which shares `JumpIfNotNull`'s arm; `HashGetLocalConst`/`HashGetGlobalConst` on a hash (the hit's value, or nil); and `GetIndex`/`GetLocalIndex` when `try_get_index_hit` answers (a hash, or an array with an in-range Int index). A zero divisor, `i64::MIN / -1`, a Float `%`, an Int/Float mix, an array or string receiver of `x["k"]` and an out-of-range index are handed back. `GetLocal, Constant, Modulo` fuses to `ModLocalConst`, as `/` fuses to `DivLocalConst`. Through 2.29.3 every one of these ops left the tier, about 4.5 ns per op. `decrement_division_nullish_and_index_reads_stay_in_the_fast_tier` (`vm.rs`), `modulo_by_a_constant_is_one_op` (`compiler.rs`) and `fast_tier_division_nullish_and_index_reads` (differential) pin it.

The instance field arms (`GetProperty`, `GetLocalProperty`, `GetPropertyOrNull`, `SetProperty` — `Vm::fast_field_read` / `fast_field_write`) answer only what the general arms' own field fast paths answer, and only when that answer involves no error: a read needs the field present (a field shadows a method, so a present key decides the read) and not a `grouped {}` placeholder, which the general arm forces, nor a model's declared relation or translated field, which the general arm resolves (`field_hit_is_raw`); a write overwrites the field or adds it, unless the instance is a constructed value object, a model or of a class with `const` fields (`has_checked_writes`), whose writes go through `set_instance_field`'s rules in the general arm (read-only `_` metadata, staged translations, const refusals). Plain objects keep both fast paths. Both run the privacy check below before they complete, and a refused access is handed back: the general arm checks it again and raises, so a refusal costs two checks while an access that passes costs one. A miss (a method, or a model member that no stored field answers), a hash write and a class receiver stay general. `GetPropertyOrNull` is the read of `obj.x ||= v` (and `&&=`, `??=`): a present field is answered as `GetProperty` answers it, except a model's relation or translated field, which goes to the resolver; a miss is Null, in the general arm. The compiler emits `obj; GetPropertyOrNull; jump END; Pop; obj; value; SetProperty; END:`, so a short-circuit writes nothing and evaluates the receiver once, as the tree-walker's `evaluate_compound_assign` does. A change to what the general arms' field fast paths answer must be made in these arms too. `field_fast_tier_tests` (`vm.rs`) counts the instance field ops the general arms run, so a field access that falls out of the fast tier shows up as a test failure.

A paren-less zero-argument builtin — `h.length`, `s.blank?`, `a.first`, `n.to_s`, the house style — is answered by the same arms. The compiler (`Compiler::get_property_op`) gives `GetProperty`/`GetLocalProperty` two more operands: the name's `resolve_method_id` and `method_registry::zero_arg_receiver_mask`, the receiver types on which that name is a zero-argument builtin (0 for a field name or a user method, which costs nothing more). The fast arm then calls `method_table::bare_zero_arg`, which answers from the integer tables `CallMethodById` uses for `h.length()`. The general arm's order is kept: a hash key comes first (`{"length": 99}.length` is 99 on the VM), a user method on the type outranks the builtin (`has_user_methods`), and `h.len`, which is no zero-argument builtin of a hash, stays a method. A name with no id (`f.round`, `i.abs`), a type the tables do not cover (symbols, instances, `DateTime`) and a value a table declines (`"zz".hex`, which raises) go to the general arm. The tables and the general arm must agree: `bare_zero_arg_agrees_with_the_general_path` (`method_table.rs`) compares them for every registered zero-argument name on a range of receivers, and `bare_builtin_fast_tier_tests` (`vm.rs`) counts the non-instance property ops the general arms run.

The instance method arm (`CallMethod` and `CallMethodById` — `Vm::fast_method`) opens the frame the general arms' compiled-method call (`call_method_slow_path` → `push_method_frame`) would open, when it would open one with nothing to pad or raise: the receiver is an instance, its class chain has the method compiled, the method takes exactly the arguments given, the depth limit is not reached, and the privacy check lets the call through. The frame carries the defining class, so `super` resolves as before. For an instance the general path resolves the nearest definition (`resolve_instance_method`, level by level: each class's compiled method, then its AST one, before its superclass's) before fields, natives and `method_missing`, and re-dispatches `send` only on a class with no `send` of its own, where that lookup misses too; so a hit decides the call. A nearest definition that is still AST is a miss here even when an ancestor's method of that name is compiled: taking the first compiled method up the chain skipped a subclass override once the parent's had run on the worker. Everything else is handed back: a native method (a model's, an uploader's), an AST-only method not compiled yet (the general arm compiles it, and later calls stay fast), `method_missing`, `send`, omitted defaults, the depth limit, a refusal (checked twice, as for fields). A change to what `call_method_slow_path` does before that lookup for an instance must be mirrored in `fast_method`.

The lookup goes through the VM's method cache (`vm/method_cache.rs`): 128 two-way sets keyed by the op's address and the receiver's class, so a polymorphic site keeps one entry per class. An entry holds the nearest definition when it is compiled (`Class::find_instance_method_level`), a miss otherwise, and is current for one method-definition epoch (`value::vm_methods_epoch`), a global counter bumped by every change to some class's `vm_methods` or `methods`. **Every writer of `vm_methods` must go through `Class::insert_vm_method` or call `note_vm_methods_changed`**; today that is `op_add_method`, `define_method`, `alias_method`, `resolve_instance_method` and `include_module`, and `Class::invalidate_method_cache` (every change to `methods`) calls it too. A redefinition is therefore seen at once, by subclasses too. An entry keeps its class and the code holding its site alive, so neither address is reused while it answers. `method_fast_tier_tests` (`vm.rs`) counts the `call_method_slow_path` entries, so a call that falls out of the fast tier shows up as a test failure.

### Iterator callbacks (`vm_callback_loop.rs`)

These methods do not loop in Rust when their callback is a compiled closure:

- hash `each`/`each_key`/`each_value`, `map`, `filter`/`select`/`keep_if`, `reject`/`delete_if`, `any?`/`all?`, `transform_values`/`transform_keys`;
- array `each`, `each_with_index`, `map`, `filter`/`select`, `reject`, `find`, `any?`/`all?`/`none?`/`one?`, `count`, `reduce`/`fold` (seeded or not) and `sort_by`;
- `Int#times`, `upto` and `downto`.

`CallMethod` hands them to `try_start_callback_loop`, and so does `CallMethodById` for `count`, the only one of them with a method id. That leaves a `CallbackLoop` on `iter_stack` and opens the first element's frame flagged `drives_loop`. When that frame returns, `Return` gives the result to the loop, which records it and refills the **same frame's** argument slots for the next element (`rerun_loop_callback`), or pops itself and pushes the method's result. That holds for a block that captured its own parameters or locals too (`groups.map { |g| g.items.map { |i| [g.name, i] } }`): the return closes those cells first, so a closure made in one pass keeps that pass's values and the next pass gets new cells. Living on `iter_stack` is what makes a `throw` out of a callback safe: `Return` and exception unwinding already truncate that stack. The loop state holds what the method needs: `reduce`'s accumulator (moved into the callback's argument slot while it runs), `find`'s element, `count`'s tally, and `sort_by`'s `(element, key)` pairs, sorted at the end with the native driver's comparator.

The callback's arguments follow the native drivers' binding rules (`ArgMode`). It receives exactly what the method passes, the first of two (`each_with_index { |x| }`; a one-parameter `reduce` gets the `[acc, item]` pair), or nothing. A block of two or more required parameters over an array element gets one part per parameter instead (`pairs.map { |a, b| … }`, with nil for a missing part). An element that is not an array then fails the way the native call does: the same arity error, at the method's call site.

A callback whose body is a **template** (`Kernel`) is not called at all: a parameter, `x + - * c`, `x < <= > >= == != c` (a number `c`), `[a, b + c]`, `[a, b]`, or `acc += x` / `acc = acc + x` into a captured variable (`GET_UPVALUE; …; ADD_ASSIGN_U`). The loop evaluates it per element in Rust. The same rule as the fast tier applies — a template computes only what its opcode's general arm answers inline (int with overflow checked, float with float); any other operand hands *that element* to the frame path, which runs the real opcodes. Templates are recognised from the exact bytecode shape (`Kernel::of`), so a peephole change that alters a callback's opcodes can make it stop matching: that is safe (it runs on the frame path), only slower. Only the one-value shapes get one. An `(item, index)` pair, `reduce`'s accumulator, an element's parts and a `[key, value]` pair argument always run the frame path.

The handler budget (`interpreter::deadline`) is checked once per element: in `next_callback` before a frame opens, in `rerun_loop_callback` before the frame reruns at ip 0 (neither path reaches `Op::Loop`), and in a template's loop over a count (`Int#times`/`upto`/`downto`, as long as the request makes it; an array or hash template is bounded by data already in memory). A spent budget ends the loop like its other errors: the callback's frame and the loop state go, and the timeout points at the method's call site. Expiry is sticky, so a `rescue` cannot resume the work. `sort_by`'s pairs are sorted with `array_ops::stable_sort_by`, the tolerant sort the native drivers use: `compare_sort_values` is no total order, and std's sort panics on that.

Everything else keeps the native drivers in `vm_hash_methods.rs` / `vm_array_methods.rs` / `vm_int_methods.rs`, whose semantics the loop mirrors element for element: live iteration with the length fixed at the start, the early exits of `find`/`any?`/`all?`/`none?`/`one?`, and the same error messages. That covers:

- a native or bound callee;
- a parameter the call would leave to its default;
- an arity the call would refuse;
- an unseeded `reduce` on an empty array;
- `sort` with a comparator;
- a function compiled to machine code (`crate::native`) whose body is not a template. The native driver calls that machine code for each element, where the loop's frame would run its bytecode.

`tests/differential_engines_test.rs` holds a case for each path. `tests/fixtures/_native/iterators.sl` covers callees compiled to machine code.

### Privacy checks

`private` and `protected` members are enforced at run time by `Vm::check_private_value` (`vm_classes.rs`), which the property, call and index ops call. It costs one relaxed load (`restricted_methods_declared()`) until some class in the process declares a restricted member. After that it still has to be cheap, because every scaffolded controller declares one. So it tries the cheap answers first, and each one is the answer the full rule would give:

1. **The receiver is the running method's `this`.** A member of `self` is never refused. When the running frame is a method frame, its slot 0 *is* the `this` the rule compares with, so `@x = v` or `@helper()` in a method's own body passes on one pointer comparison. `GetLocalProperty(0, …)` in a method frame, which is what `@x` compiles to, does not call the check at all, in either tier.
2. **No class of the receiver's chain restricts the name.** `Class::restricted_method` first asks the class's `restricted_names_memo`: the set of names that some class of the chain declares private or protected. A name outside that set cannot be restricted, so the check returns without walking the chain and without looking at the call frames. This covers every field of a class with no restricted member, from any call depth, and `@x` inside a block when `x` is not restricted.
3. **The name is restricted.** Only now does the check look for `this` past the blocks a method runs. `current_this()` scans the frame stack down to the nearest method frame, so from a plain function it visits every frame. A member of that `this` passes, which is how a block reaches its method's private members.
4. **Otherwise** a protected member passes when the caller's class is or inherits the defining class. Anything else is refused with the usual message and span.

`restricted_method` decides by walking the chain until a class defines the name, so the nearest definition wins: a subclass that redefines a private method without a modifier makes it public again.

The memo is valid for one `RESTRICTED_MEMBERS_EPOCH`. **Code that adds a name to a class's `private_members` or `protected_members` after the class exists must call `note_restricted_methods_declared()`.** Where the flag must not change (a nested `private class`), call `note_restricted_members_changed()` instead. Skip both and every class below keeps a stale memo and stops refusing that name. A cloned `Class` starts with an empty memo. `restricted_member_tests` (`value.rs`) and `privacy_check_tests` (`vm_classes.rs`) count lookups, walks and frame scans, so a lost shortcut shows up as a test failure. The `privacy_*` differential cases pin the verdicts.

### Static calls

`Klass.name(args)` resolves in one walk up the chain (`resolve_static_callee`, `vm_calls.rs`) and is called from there. On each class, receiver first: its bytecode statics (`vm_static_methods`), its cached plain statics (`vm_plain_static_methods`), then the tree-walker's own `static_methods` and the methods `extend` mixed in. So a subclass's static hides its superclass's, whichever form either is in, as on the tree-walker.

Under `soli serve` the app's classes come from the tree-walker, so most statics are tree-walker `static def`s. The first call compiles one. A static that reads `this` is compiled as a method and registered in the defining class's `vm_static_methods`; it runs with the class it was called on as `this`. Any other static is compiled as a plain function, the same bytecode `call_native_wrapper` would make, and runs with no class on the frame. When it is one of the class's own `static_methods`, its `VmClosure` is kept in `vm_plain_static_methods`, so the next call costs two ahash probes and allocates nothing. That map never changes once the class is built, and a cloned `Class` starts with an empty cache. An `extend`ed method is compiled but not cached, because reopening a module replaces those. A view VM (`tree_walk_functions`) leaves plain statics to the tree-walker, as it does other functions.

When no class of the chain has the static, a native static of a non-model class (`Math.floor`, `DateTime.utc`) is called directly. Model natives, which take the class as their first argument, still go through `op_get_property`. So do static fields, the reflection surface, dynamic finders and, last of all, the class's `method_missing`.

## `Vm`

```rust
pub struct CallFrame { /* proto, ip, stack_base, … */ }

impl Vm {
    pub fn new() -> Self
    pub fn execute(&mut self, proto: &Arc<FunctionProto>) -> Result<Value, RuntimeError>
    pub fn run(&mut self) -> Result<Value, RuntimeError>
    pub fn push(&mut self, value: Value)
    pub fn pop(&mut self) -> Value
    pub fn peek(&self, distance: usize) -> &Value
    pub fn close_upvalues(&mut self, from_slot: usize)
}
```

`execute` sets up a frame and calls `run`. `run` loops: fetch `Op` at `ip`, execute, increment `ip` (or jump).

Stack slots are `Value`. Locals are slots relative to `CallFrame.stack_base`.

Closures (`vm_upvalues.rs`; the types are in `upvalue.rs`): a captured local becomes a cell, `Rc<RefCell<Upvalue>>`, shared by every closure over that variable. It is *open* on the variable's stack slot while the variable lives and *closed*, holding the value, once it goes out of scope — the Crafting Interpreters “move to heap when the stack slot dies” step. `open_upvalues` lists the open cells with their slots, sorted by slot, so `close_upvalues(from)` pops a tail, and `open_upvalue_top` tells a return in one comparison whether its frame has any. Variables go out of scope at a frame's `Return`, at a scope's `CloseUpvalue` (a captured loop variable, a block's `let`), and when an exception unwinds: everything above the handler's stack depth is closed, the `try` body's own locals included.

Evaluating a `fn` expression allocates nothing once warm:

- a closure that captures nothing is one shared instance per expression (`closure_cache`);
- a capturing block that an iterator loop held the last reference to when it finished is kept with its upvalues emptied, and the next evaluation of the same expression refills it (`closure_spares`, `recycle_closure`);
- a cell nothing else references when its variable goes out of scope is not given the value: it goes back to `upvalue_pool` for the next capture.

Each reuse needs the only reference (`Rc::get_mut`, or a strong count of 1 and no weak one), so no live closure can tell. Both caches are direct-mapped by the prototype's address, all of its bits mixed (`closure_slot`): prototypes share one allocator size class, and `(address >> 4) % 64` reached only 16 of the 64 slots.

`total += x` and `total = total + x` into a captured variable compile to one `AddAssignUpvalue`, a variable or literal `x` included: a local leaves those to its peepholes (`IncrLocal`, `AddLocalsInPlace`, …), and a captured variable has none. The exception is `acc = acc + h[keys[k]]` over variables, which stays `Add` and `SetUpvalue` whatever `acc` is, because over locals it is the `AddNestedIndex` peephole's. The fast tier runs `AddAssignUpvalue` on numbers; a string grows in place in the general arm.

Errors carry the same `line:column` as the tree-walker's: `Chunk` keeps a `columns` vector parallel to `code` (`emit_at` records the column of the expression or statement being compiled, 0 where unknown). The call-depth error names the function and points at its declaration, worded as the tree-walker words it (`call stack too deep (256 frames) in "down" — unbounded recursion?`).

`Vm::check_return_types` checks a function's or method's declared return type when it returns (`FunctionProto` keeps it), with the tree-walker's message (`function 'f' expected to return Int, got null`). `run_compiled_on_vm` in `lib.rs` turns it on, so scripts get it; `soli serve` leaves it off, as apps have always run.

## Native methods on the VM

`vm_string_methods.rs`, `vm_array_methods.rs`, `vm_hash_methods.rs`, `vm_int_methods.rs`, `vm_primitive_methods.rs` implement **the same** methods as the interpreter builtins, but they take stack values and must not allocate an `Interpreter` for the happy path.

If interpreter and VM diverge, users see “works in tests, fails in production” (or the reverse). Add both, then a differential test.

## Seeding builtins

`run_vm` in `lib.rs` builds a throwaway `Interpreter::new()`, then copies its globals into the VM so `DateTime`, `HTTP`, `File`, … exist. Serve workers do the same once at boot (`engine_loader`).
