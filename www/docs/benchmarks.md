# Benchmarks: Soli vs Ruby

Reproducible per-operation numbers comparing Soli's production engine against Ruby. The
scripts ship in `bench/cross-language/` so you can re-run them yourself.

> **Read this first.** Benchmarks are easy to rig and easy to get wrong — this page has
> already been corrected once. Everything below is best-of-7 on **byte-identical inputs**
> (generated by the same LCG in both languages), and Ruby is credited with its **best**
> result across three modes, not its slowest. Where Soli loses, the number is printed
> exactly as measured.

## Setup

| | |
|---|---|
| Soli | production bytecode VM (`soli --vm`) |
| Ruby | 4.0.6 — default, `--yjit`, `--zjit` |
| Method | best-of-7 per operation, warmed once first |
| Data | n = 20,000; identical LCG-generated inputs in both languages |
| Machine | idle 16-core x86-64 Linux |

`ratio` is Soli ÷ Ruby's *best* mode. **Below 1.00 means Soli is faster.**

## Summary

| Category | Geometric mean | Soli wins |
|---|---:|---:|
| String | 0.37x — Soli **2.7x faster** | 11/13 |
| Array | 1.15x — Soli 1.1x slower | 7/16 |
| DateTime | 2.54x — Soli 2.5x slower | 1/9 |
| Hash | 2.18x — Soli 2.2x slower | 1/11 |
| Duration | 9.08x — Soli 9.1x slower | 0/2 |
| Numeric | 3.83x — Soli 3.8x slower | 0/3 |
| Control | 3.80x — Soli 3.8x slower | 0/2 |
| **Overall** | **1.36x** | **20/56** |

Soli is ahead on **20 of 56** operations, but behind on the
geometric mean. The split is not random — it tracks *where the work happens*:

- **Inside Rust** (string transforms, `flatten`, `union`, `sort`, `DateTime.parse`) — Soli
  wins, often by 3-30x.
- **Per-element in interpreted code** (arithmetic loops, function calls, blocks, hash
  iteration) — Ruby wins by 2-6x.

If your hot path transforms data with built-in methods, Soli is faster. If it is a tight
hand-written loop, Ruby's JIT is faster.

## Why the split exists

Soli's `Value` is 24 bytes; Ruby's `VALUE` is 8 with tagged fixnums, so every stack push and
pop in a Soli loop moves three times the memory and pays a discriminant check. Ruby also
dispatches through direct-threaded code and, with YJIT/ZJIT, compiles hot loops to machine
code. Soli's VM uses a `match` dispatch and interprets every iteration — a bare
`while` loop costs ~45 ns/iteration against ZJIT's ~13 ns.

Against that, Soli's built-in methods are compiled Rust over native data structures, which
is why the same tables show `capitalize` at 15x and `DateTime.parse` at 29x.

Closing the loop gap is a VM representation project — pointer tagging or NaN-boxing plus
threaded dispatch — not something library tuning can reach.

## What this does not measure

Micro-benchmarks of individual operations. They say nothing about end-to-end web request
throughput, where framework architecture, the database and I/O dominate, and where Soli's
threaded worker model behaves very differently from a Ruby process fleet. Treat this as a
guide to *which operations are cheap*, not a verdict on either language.

## Corrections

This page's first version reported an overall **0.99x** (a dead heat). That was wrong, and
the cause is worth stating: the input data flattered Soli.

- `sort` ran on an **already-sorted** array, where Rust's sort detects the ordered run and
  goes O(n) while Ruby's does not — it measured run-detection, not sorting.
- `intersection` / `difference` / `union` ran on two **identical** arrays (100% overlap, empty
  difference) — degenerate cases.
- `flatten` ran on a **flat** array, never exercising the recursion it exists for.
- `uniq` ran on **all-unique** input.

All are now fixed: shuffled LCG data, 50%-overlapping ranges for set operations, genuinely
nested input for `flatten`, and duplicate-heavy input for `uniq`. The honest overall figure
after the fix is **1.42x**, and `sort` — which had looked like a 5x win — is now a real but
modest 0.86x.

## Reproducing

```bash
soli --vm bench/cross-language/bench_all.sl
ruby        bench/cross-language/bench_all.rb   # add --yjit / --zjit
```

Both print `category|operation|best_ms`.
