# Benchmarks: Soli vs Ruby

Reproducible per-operation numbers comparing Soli's production engine against Ruby. The
scripts ship in `bench/cross-language/` so you can re-run them yourself.

> **Read this first.** Benchmarks are easy to rig and easy to get wrong — this page has
> already been corrected once (see [Corrections](#corrections)). Everything below is
> best-of-7 on **byte-identical inputs** generated by the same LCG in both languages, and
> Ruby is credited with its **best** result across three modes, not its slowest. Where Soli
> loses, the number is printed exactly as measured.

## Setup

| | |
|---|---|
| Soli | production bytecode VM (`soli --vm`) |
| Ruby | 4.0.6 — default, `--yjit`, `--zjit` |
| Method | best-of-7 per operation, warmed once first |
| Data | n = 20,000; identical LCG-generated inputs in both languages |
| Machine | idle 16-core x86-64 Linux |

`ratio` is Soli ÷ Ruby's *best* mode. **Below 1.00 means Soli is faster.**

## Summary

| Category | Geometric mean | Soli wins |
|---|---:|---:|
| String | 0.36x — Soli **2.8x faster** | 11/13 |
| Aggregate | 0.39x — Soli **2.5x faster** | 11/11 |
| Array | 1.24x — Ruby 1.2x faster | 6/16 |
| Hash | 2.19x — Ruby 2.2x faster | 2/11 |
| DateTime | 2.58x — Ruby 2.6x faster | 1/9 |
| Numeric | 4.13x — Ruby 4.1x faster | 0/3 |
| Control | 4.79x — Ruby 4.8x faster | 0/2 |
| Duration | 9.16x — Ruby 9.2x faster | 0/2 |
| **Overall** | **1.14x** | **31/67** |

The split is not random — it tracks **where the work happens**:

- **Inside Rust** — string transforms, `flatten`, `sort`, `DateTime.parse`, and the whole
  Aggregate family — Soli wins, often by 3–30x.
- **Per-element in interpreted code** — arithmetic loops, function calls, blocks, hash
  iteration — Ruby wins by 2–4x, because its JIT compiles those loops to machine code.

The practical lesson is in the Aggregate row. `rows.sum_by("amount")` and
`rows.reduce(fn(a, r) { return a + r["amount"] }, 0)` compute the same thing, but the first
stays in Rust and the second re-enters the interpreter 20,000 times — a **235x** difference,
and the difference between beating Ruby and losing to it. Prefer the built-in.

## Aggregate

Field-keyed aggregates: `rows.sum_by("amount")` rather than `rows.reduce(fn(a, r) ...)`. Because the field name is data rather than a callback, the whole traversal stays in Rust and never re-enters the interpreter. Ruby has no non-block form of these, so its versions pay a block call per element — which is precisely the cost being avoided.

## Why the split exists

Soli's built-in methods are compiled Rust over native data structures, so an operation that
never re-enters the interpreter runs at Rust speed. An operation that calls back into Soli
once per element pays ~44 cycles per bytecode dispatch, and Ruby's JIT compiles the
equivalent loop to machine code — an entire ZJIT iteration fits inside one Soli dispatch.

That is the whole story of this page. It is also why the fix for a slow Soli program is
usually to reach for a built-in rather than to hand-write the loop.

## What this does not measure

Micro-benchmarks of individual operations. They say nothing about end-to-end web request
throughput, where framework architecture, the database and I/O dominate. Treat this as a
guide to *which operations are cheap*, not a verdict on either language.

## Corrections

This page's first version reported an overall **0.99x**. That was wrong: the input data
flattered Soli. `sort` ran on already-sorted input (Rust detects the ordered run and goes
O(n); Ruby does not), the set operations ran on two identical arrays, `flatten` on a flat
array, and `uniq` on all-unique input. All are fixed — shuffled LCG data, 50%-overlapping
ranges, genuinely nested input, duplicate-heavy input — and `sort`, which had looked like a
5x win, is a real but modest one.

## Reproducing

```bash
soli --vm bench/cross-language/bench_all.sl
ruby        bench/cross-language/bench_all.rb   # add --yjit / --zjit
```

Both print `category|operation|best_ms`.
